# Plain Deep Report specification

This is the default reader product. It must reproduce the compact editorial system established by `4PIE_*_Plain_Deep_Report_v1`; visual similarity alone is insufficient.

The canonical renderer is `scripts/render_plain_deep_pdf.py`. Do not substitute the Dashboard renderer.

## Page order

1. Restrained 4PIE cover.
2. Generated table of contents and reading route.
3. Formula-backed domain scores with definitions.
4. Requested time index using approved annual rulings only.
5. Deep prose: five discriminating conclusions, personality, career, wealth, relationship, home/family, network/reputation, learning, stress and timing.
6. Technical boundary and concise evidence appendix.

## Fixed visual contract

- Warm `#F7F4EE` background and navy `#17324D` typography.
- Mountain-and-route cover graphic with left-aligned 4PIE title.
- Contents made from alternating pale-blue and white rounded cards with page numbers.
- Eight-domain score page in a two-column, four-row card grid with four horizontal bars.
- Five-year vertical timeline using green, blue, purple, amber and green cards.
- Editorial body with pale-blue chapter bands, compact typesetting, footer rule and page number.
- First four pages are fixed modules; body length follows content.
- Every cover field, score, year, thesis and ruling is read from the current case. The 2002 reference case supplies design only and must never supply content.

## Production gate

Do not render when any core school, Bazi L1, dossier, adjudication position, score row, requested year or Reader section is incomplete. Eight score rows and four numeric metrics per row are mandatory. The requested five-year range must be explicit and consecutive.

Do not insert the expanded method cards, consensus matrix or decision-table dashboard before the Reader unless the user requests the Dashboard edition. Those artifacts remain available in JSON and the appendix.

## Writing density

- Prefer 12-16 information-dense pages over 20-30 sparse dashboard pages.
- Each major domain must compare at least two plausible life versions and state why one ranks higher.
- Put the plain-language ruling first. Technical configuration follows as evidence.
- Do not turn analysis into coaching checklists. Advice is secondary and visibly labelled.
- Never reuse a previous subject's prose, scores, dates, stems, branches or life story.
